## 1. 结论

**不会破坏。** 因为要做的唯一一件事是**新增一张表**，它不动任何现有表、不删任何现有数据。

而且这次不是推演——在你的真实数据库副本上跑了完整的迁移演练，5 项判据 × 2 个库**全部通过**（见第 2 节）。

最关键的一条性质：**新表是"派生数据"，不是事实来源。** 它里面的每个数字都能从原表重新算出来。所以任何时刻把它整个删掉，应用都该能照常运行（退回慢查询或自己重建）——判据 D 已经验证了这一点。

真正会出事的是另外几种改法（改列、重建表、加非空列），第 3 节列了红线。

## 2. 演练结果（在真实库副本上实测）

方法：把 `key_data.db` / `click_data.db` 只读拷贝到临时目录，在副本上执行完整迁移，通过 5 项判据。**真实数据全程只读，未被触碰。**

| 判据 | 含义 | key_data.db | click_data.db |
|---|---|---|---|
| A | 原始表行数与内容校验和不变 | 通过（1,927,850 → 1,927,850，校验 `5fe788530bc6ce13` 不变） | 通过（394,570 → 394,570，校验 `08ccc09220fea7cd` 不变） |
| B | 现有 app 的查询结果完全一致 | 通过（校验 `bb86cb19c81e5ebe` 不变） | 通过（校验 `bc00e160d78006c7` 不变） |
| C | 迁移重复执行结果一致（幂等） | 通过 | 通过 |
| D | 删掉新表可完全回滚 | 通过 | 通过 |
| E | 旧版本 app（不认识新表）读写正常 | 通过 | 通过 |

回填开销实测：

| 库 | 原表行数 | 回填耗时 | 生成聚合行数 | 计数合计 vs 行数 | 体积增量 |
|---|---|---|---|---|---|
| key_data.db | 1,927,850 | **2.49 s** | 11,121 | 1,927,850 = 1,927,850 ✓ | 85.4 → 85.9 MB（**+0.5 MB**） |
| click_data.db | 394,570 | **0.50 s** | 315 | 394,570 = 394,570 ✓ | 18.0 → 18.0 MB（**+0.0 MB**） |

"计数合计 = 原表行数"这一条很重要：它说明聚合表没有多算也没有漏算。

顺带一个旁证：两次演练之间 `ClickRecords` 从 394,559 涨到 394,570（+11 行）——说明演练期间真实应用仍在正常写入，我们没干扰到它。

判据 A–D 对应的是"原始数据一字未改"，判据 E 对应的是"用户降级也安全"。这五条合起来就是"非破坏性"的定义。

## 3. 改什么 / 不改什么

### 要改的（全部是新增）

| 项 | 位置 | 说明 |
|---|---|---|
| 新表 `KeyDaily(Date, Key, Cnt)` | `key_data.db` | 键盘日聚合，主键 `(Date, Key)` |
| 新表 `ClickDaily(Date, Button, Cnt)` | `click_data.db` | 点击日聚合，同一套路 |
| 新表 `AggMeta(Name, Value)` | 两个库各一份 | 记录 `AggregatedThrough`（回填到哪天），保证幂等与自愈 |
| 写入路径追加一条 UPSERT | `KeyDatabaseService.SaveKeyPress` / `ClickDatabaseService.SaveClick` | 同一连接、同一事务内先 INSERT 原表再 UPSERT 聚合表 |
| 新增聚合查询方法 | 两个 Service | 供新界面用 |

### 不改的（红线，碰了就真会出事）

| 禁止 | 原因 |
|---|---|
| `DROP TABLE` 任何现有表 | 直接删用户数据 |
| `ALTER TABLE` 改列类型或列名 | SQLite 会重建表，中途失败即数据损坏 |
| 用"建新表 + INSERT SELECT + RENAME"重建现有表 | 同上，且大库耗时可能几十秒 |
| 给现有表加 **`NOT NULL` 且无默认值**的列 | **有前车之鉴**：`quick_notes` 表加这种列曾导致直插写入静默失败（见 `CLAUDE.md`） |
| `DELETE FROM` 清理历史数据 | 用户的数据不是我们该替他删的 |
| 改数据库文件名 / 目录 / `appsettings.json` 现有键名 | 用户升级后会"数据消失" |

## 4. 五条纪律

1. **只增不删（additive-only）。** 迁移只做 `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` / 加带默认值的列。永远不删、不改、不重建。
2. **每一次执行都必须幂等。** 用 `IF NOT EXISTS` + `ON CONFLICT ... DO UPDATE` + 带守卫的回填。用户可能一天开二十次 app，迁移代码会跑二十次。
3. **新表是派生的。** 任何时刻它被删掉/损坏，应用必须能降级运行（退回慢查询）或自己重建。做不到这一点，就不该建这张表。
4. **迁移失败绝不拦启动。** 全部 `try/catch` + 记警告日志，然后退回慢查询路径。宁可慢，不能打不开。
5. **回填在后台跑，可中断可续跑。** 不阻塞启动、不阻塞录制。192 万行 2.5 秒是我这台机器；别人可能更多，按线性外推 1000 万行约 13 秒。

## 5. 代码里已有的两个参照点

### 参照点 1（正面）：这条路走过

`Services/ProcessUsageTracker.cs:137-153` 已经用过加列迁移，写法是可取的：

```
foreach (var col in new[] { "AccumulatedSeconds REAL NOT NULL DEFAULT 0", "LastUpdateTime TEXT" })
{
    try { ... "ALTER TABLE ProcessSession ADD COLUMN {col}" ... }
    catch (SqliteException ex) when (ex.Message.Contains("duplicate column")) { }
    catch (Exception ex) { _logger.LogWarning(ex, "添加列 {Col} 异常", col); }
}
```

三个好习惯都在：**加列带默认值**、**重复执行靠吞 `duplicate column`**、**其他异常降级成警告**。新表的迁移照这个调子写。

### 参照点 2（要避开的写法）：用状态值当"旧记录"判据

`Services/ProcessUsageTracker.cs:168-175`：

```
UPDATE ProcessSession
SET EndTime = StartTime, AccumulatedSeconds = 0, LastUpdateTime = StartTime
WHERE EndTime IS NULL AND AccumulatedSeconds = 0;
```

这段每次 `Start()` 都会跑（`Start()` 第 44 行调 `InitializeDatabase()`）。它想处理的是"以前 bug 残留的未完成会话"，但判据用的是 `AccumulatedSeconds = 0` —— 这不是可靠判据：任何"会话已开始、但 5 秒累计定时器还没跑过"的会话都满足条件，会被直接关闭并把时长清零。

在单进程、且这段跑在 `CaptureExistingProcesses()` 之前的情况下恰好不会命中自己的新会话，所以现在没暴雷。但它演示了一类危险写法：**"用状态值推测记录的新旧" + "每次启动都无差别执行"**。新表的回填**不要**用这个模式，要用第 7 节那种显式的进度标记。

## 6. 现在缺的一样东西：schema 版本号

现状：三个库都没有版本概念，全靠 `CREATE TABLE IF NOT EXISTS` + 吞 `duplicate column` 异常维系。单用户时够用。

开源之后用户库的状态会分化：有的从 v1.0.0 一路升、有的全新装、有的中间跳版本、有的手工改过。靠"猜有没有这张表"来判断该不该迁移，很快就会失控。

**建议：引入 `PRAGMA user_version`，单调递增。** 迁移按版本号判断，而不是按表存在性猜。这是本次改造里唯一一个"现在不做、以后会更贵"的事，建议跟预聚合表一起做掉。

## 7. 回填设计（幂等 + 自愈 + 不阻塞启动）

```
启动
 └─ 后台线程执行 EnsureAggregates()
      ├─ CREATE TABLE IF NOT EXISTS KeyDaily / AggMeta      ← 本来就幂等
      ├─ 读 AggMeta.AggregatedThrough
      │    ├─ 为空 / 表刚建  → 从 0 全量回填
      │    └─ 有值          → 只补 日期 > AggregatedThrough 的部分
      ├─ 回填用 ON CONFLICT(Date,Key) DO UPDATE SET Cnt=excluded.Cnt   ← 重复跑结果一致
      ├─ 成功 → 写回 AggregatedThrough = 最新日期
      └─ 失败 → 只记警告日志，界面退回慢查询（纪律 4）
```

自愈：若 `KeyDaily` 被删或损坏，启动时检测到缺表/缺行 → 从 0 全量重建（key 库 2.5 秒）。因为它是派生数据，重建永远安全。

写入侧：

```
同一个 SqliteConnection、同一个事务：
  INSERT INTO KeyPressRecords (Key, PressTime) VALUES (@k, @t);
  INSERT INTO KeyDaily (Date, Key, Cnt) VALUES (@d, @k, 1)
    ON CONFLICT(Date, Key) DO UPDATE SET Cnt = Cnt + 1;
```

注意：**先写原表，聚合表失败不回滚原记录**（纪律 3 的具体体现——原表是事实来源，聚合表可以事后补）。这一点在实现时要在事务边界上想清楚，别为了"一致性"把原记录的写入也拖下去。

## 8. 降级与回滚

| 场景 | 结果 | 依据 |
|---|---|---|
| 用户升级后装回旧版本 | 旧版本只 SELECT 自己的表，多出的表完全不引用 → 正常 | 判据 E 已验证 |
| 想彻底撤销这次改造 | `DROP TABLE KeyDaily / ClickDaily / AggMeta` → 原表校验和与旧查询结果一字不差 | 判据 D 已验证 |
| 新表数据算错了 | 删掉重建，从原表重算 | 派生数据的性质 |

## 9. 还没验证的

- **与真实 app 二进制的联调。** 本次只用 SQL 层演练，没有跑改造后的 `XAssistant.exe`。实现完要在 Debug 版（`%APPDATA%\XAssistant_Dev`）上跑一遍完整流程。
- **多实例并发写。** 两个 XAssistant 同时运行时，原表 INSERT + 聚合 UPSERT 在同一事务里，SQLite 的锁竞争与 `database is locked` 重试策略没测过。
- **超大库的回填耗时。** 本机 192 万行 2.49 秒，1000 万行约 13 秒是线性外推，没实测。
- **WAL 与否的差异。** `key_data.db` / `click_data.db` 目前是默认回滚日志模式（没有 `-wal` 文件），只有 `app_usage.db` 是 WAL。是否要一并改 WAL，会同时影响读写性能与并发，没测。

## 10. 验收清单

改造完成后逐条勾：

- [ ] 在 Debug 数据目录上跑一遍：新表建好、回填完成、`SUM(Cnt)` 等于原表当日行数
- [ ] 重复启动 5 次：`AggregatedThrough` 不回退、`KeyDaily` 行数不变
- [ ] 手工 `DROP TABLE KeyDaily`：下次启动能自动重建
- [ ] 把 `KeyDaily` 内容改错一行：能看到界面数字不一致（说明一致性校验真在跑）
- [ ] 迁移过程中强杀进程：下次启动能续跑，原表不受影响
- [ ] 用 v1.0.0 的 exe 打开改造后的库：能正常读写（判据 E 的真实版）
- [ ] 改造后的键盘页任意范围切换 < 50 ms
- [ ] 全库备份一次（`cp key_data.db key_data.db.bak`）作为上线前快照
