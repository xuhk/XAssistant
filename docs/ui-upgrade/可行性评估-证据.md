## F. WebView2 上真机实测

为回答"常驻后台会不会被拖慢"，直接搭了最小 WPF 宿主真跑，而不是查文档。4 个探针工程在 `temp/wv2-probe/`，各自的结果文件同目录。

环境：Windows，4 逻辑核，WebView2 运行时 **153.0.4234.48**（已装），`Microsoft.Web.WebView2` 包按 `1.0.*` 解析，加载页面为 **v4 真实页面**（`temp/ui-design/v4/index.html`），不是空白页。

### F1 包体积增量

| 文件 | 体积 |
|---|---|
| `Microsoft.Web.WebView2.Core.dll` | 698,208 B（682 KB） |
| `WebView2Loader.dll` | 163,680 B（160 KB） |
| `Microsoft.Web.WebView2.Wpf.dll` | 87,392 B（85 KB） |
| **合计增量** | **≈ 1.0 MB** |

对照：整个探针 FDD publish 13 个文件 / 2.05 MB（含探针自身 exe 与 xml 文档）。

### F2 三段内存（`probe-result.txt`，三轮开关循环）

宿主基线：工作集 37.5 MB / 私有 10.5 MB / 线程 8。

| 阶段 | 宿主私有 | WebView2 子进程 | 合计私有 | 合计工作集 |
|---|---|---|---|---|
| 基线 | 10.5 MB | 0 | 10.5 MB | 37.5 MB |
| 只建 Environment | 11.8 MB | 0 | 11.8 MB | 40.6 MB |
| 主窗打开 + 首帧后静置 4s | 80.1 MB | 6 个 / 私有 243 MB | **323 MB** | ~441 MB |
| 释放 5s 后 | 82.2 MB | **0 个 / 0 MB** | 82.2 MB | 92.8 MB |
| 再 trim 工作集 | 82.2 MB | 0 | 82.2 MB | **12.1 MB** |

三轮循环的"释放 5s 后"分别是 82.2 / 83.8 / 84.1 MB，**不涨台阶**；子进程每轮都是 **0 残留**。

关键点：工作集能被 trim 到 12.1 MB，而私有提交量停在 82 MB —— 说明释放确实是干净的，只是已提交的页仍计入提交量。

### F3 残留归属（`residue-result.txt`）

为区分"托管堆没回收"还是"原生残留"，同时记录 `GC.GetTotalMemory(true)` 与模块数：

| 阶段 | 私有 | 托管堆 | 非托管残留 | 工作集 | 已加载模块 |
|---|---|---|---|---|---|
| 基线（WPF 已起，未碰 WebView2） | 11.5 MB | 0.3 MB | 11.2 MB | 39.0 MB | 76 |
| 只建 Environment | 11.4 MB | 0.3 MB | 11.1 MB | 41.0 MB | 80 |
| 页面已加载 | 80.8 MB | 1.0 MB | 79.8 MB | 90.7 MB | **145** |
| 控件已 Dispose + GC + trim | 82.5 MB | 1.0 MB | 81.5 MB | 24.6 MB | 146 |
| env 引用也丢掉 + GC | 81.0 MB | 1.0 MB | 80.0 MB | 15.1 MB | 146 |
| 延迟 5s 后 | 81.2 MB | 1.0 MB | 80.2 MB | 13.4 MB | 146 |

**判定：托管堆始终只有 1.0 MB**，+70 MB 全在非托管侧，且**模块数 76 → 146（+70 个 DLL）**。

成因：WebView2 把 70 个 DLL 加载进宿主进程，而 Windows 与 .NET 都不支持卸载已加载模块。所以"用一次就永久留下"，丢掉 env 引用、强制 GC、trim 工作集都无法回收。

### F4 首帧耗时与预热有效性

| 实验 | 第 1 轮 | 第 2 轮 | 第 3 轮 |
|---|---|---|---|
| 复用 Environment（`probe-result.txt`） | CoreReady 2590 ms / 首帧 3323 ms | 951 ms / 3600 ms | 1165 ms / 3283 ms |
| **每轮新建 Environment**（`warm-result.txt`） | CoreReady 4116 ms / 首帧 4604 ms | 2113 ms / 3421 ms | **1007 ms / 3129 ms** |

每轮都新建 env 时 CoreReady 依然从 4116 → 1007 ms，**说明提速来源是"70 个 DLL 已加载进进程"，不是 env 复用**。

但注意：CoreReady 降到 1.0 s 后，**首帧仍是 3129 ms**。CoreReady 与首帧之间那约 2.1 s 是 v4 页面自身渲染（365 格热力 + 104 键 + 手写 SVG）的开销，预热消不掉。

→ 预热只能把冷启动 4.6 s 改善到 3.1 s；**骨架屏无论如何都得上**。

### F5 空闲 CPU（`cpu-result.txt`）

采样 10 s，折算单核百分比：

| 窗口状态 | 消耗 CPU | 折合单核 | 折合整机（4 核） |
|---|---|---|---|
| 可见、前台（静置 4s 后） | 0.64 s | 6.4% | 1.60% |
| 最小化 | 0.05 s | 0.5% | 0.12% |
| 隐藏（等价于关到托盘但保留控件） | 0.11 s | 1.1% | 0.27% |
| 重新可见后 | 0.05 s | 0.5% | 0.12% |

第一组 6.4% 含加载收尾与 JIT 的余量——"重新可见"回落到 0.5% 就是证据。**v4 页面的过渡与动效没有造成常态化 CPU 消耗。**

### F7 本次仍未验证的

- **已安装 `Microsoft.Web.WebView2` 的宿主进程与 `XAssistant.exe` 一起跑**时的真实叠加值。上面 F2/F3 的宿主是空 WPF 壳（基线私有 10.5 MB），而真实 `XAssistant.exe` 常驻私有是 **122.0 MB / 工作集 78.8 MB**。叠加后预期 **私有 ~192 MB、工作集 ~90–100 MB**，但这个数字是推算的，没有实测。
- **独立 UI 子进程方案**（把主窗放进另一个进程，关窗即整个进程退出，从而避免那 +70 MB 常驻）。理论上能把这 70 MB 完全消掉，代价可能是每次开窗都付冷启动。没有实测。
