# APP 界面升级可行性评估（v4 → XAssistant）

## 〇、一句话看懂（不看下面细节也能决策）

- **该不该做**：该做。v4 那套界面是能跑的东西，不该推倒重画。
- **要不要用网页技术**：要用。C# 原生要把 104 键热力图、365 格年热力、24 小时时间轴这些全从零画一遍，代码量翻倍，还做不出 v4 那种观感。
- **会不会拖慢系统**：**不会。** 平时挂着 ≈79 MB，跟现在一样。只有你打开主窗看数据那几分钟涨到 ≈480 MB，关掉 3 秒内就还回去。CPU 几乎不动（占整机 0.12%）。
- **要付什么代价**：用过一次之后，进程里永久多占 70 MB 的"预定额度"。这额度不占实际内存（系统会把它换出去），但确实退不回来。
- **两个必须先解决的**：① 打开主窗要等 3 秒才出画面 → 得先画个骨架顶着；② 键盘页现在取数要 4 秒 → 得先把数据库改成预聚合表，**这个比界面更优先**。
- **一条不能碰的红线**：速记小窗（热键唤起那个）必须保持原生。它要求按一下就出来，网页技术做不到。

## 1. 结论

**你的判断是对的：WebView2 是不得不选，而且实测证明它在"常驻不拖慢系统"这条上是合格的。**

四条判断：

1. **常驻这条要求满足。** 懒加载 → 开机路径完全不碰 WebView2；不开主窗时零成本；开过再关，浏览器子进程 3–5 秒内全部退出、三轮开关不涨台阶；空闲 CPU 整机 0.12%，可忽略。
2. **但有一个必须先解决的体验问题：首帧 3.1–4.6 秒。** 点了主窗以后要等 3 秒以上才出画面。这其中约 2.1 秒是 v4 页面自身渲染（365 格热力 + 104 键 + SVG 图表）的开销，预热不掉。**骨架屏从"可选"升级为"必须"。**
3. **代价是一次的、不可逆的 +70 MB。** 第一次用过 WebView2 之后，宿主进程会永久多占约 70 MB 私有提交量（它把 70 个 DLL 加载进了进程，Windows/.NET 都不支持卸载）。但这是**提交量不是物理内存**——工作集会被内核 trim 回落（实测 trim 后仅 13 MB），所以不直接压物理内存。
4. **包体积增量只有 1.0 MB。** 这点比预期还好，对"轻量"几乎没有伤害。

原生重写（路线 A）依然不推荐：工作量 5,000–7,000 行（≈现有仓库 1.0–1.4 倍），而且 v4 那 140 KB 已验资产全部作废。

## 2. 你最担心的这条：常驻后台会不会被拖慢

全部为实测值（4 逻辑核机器，WebView2 运行时 153.0.4234.48，加载的是 v4 真实页面）：

| 场景 | 实测结果 | 判定 |
|---|---|---|
| 开机自启动，未开主窗 | 懒加载 → 完全不创建 WebView2，宿主私有 11.5 MB 基线不变 | **零影响** |
| 常驻但从未开过主窗 | 无任何 WebView2 相关进程与内存 | **零成本** |
| 打开主窗 | 自身 +90 MB 工作集；6 个 `msedgewebview2` 子进程 350 MB 工作集 / 250–280 MB 私有；**合计约 440 MB** | 瞬时重，仅在此期间 |
| 关掉主窗后 3–5 秒 | 子进程 **0 残留**；连开三轮不涨台阶 | **干净退出** |
| 关掉主窗后的宿主 | 私有 11.5 → **81.2 MB（+70 MB，不可逆）**；托管堆仅 1.0 MB → 纯原生残留；已加载模块 76 → 146 | 一次性成本，不压物理内存 |
| 空闲 CPU（可见） | 单核 0.5% / 整机 0.12% | **可忽略** |
| 空闲 CPU（最小化 / 隐藏） | 单核 0.5% / 1.1% | **可忽略** |
| 首帧耗时 | 冷 **4.6 s** → 第二次 3.4 s → 进程已加载过后 **3.1 s** | **必须骨架屏** |
| 包体积增量 | **+1.0 MB**（Core 682 KB + Loader 160 KB + Wpf 85 KB） | **可忽略** |

关于那 +70 MB，要讲清两点，不然容易误判：

- **它是私有提交量，不是物理内存。** 工作集在释放后被内核 trim 回落（实测 trim 后只有 13 MB），被换出的页不占物理内存。所以它占的是提交配额/页面文件，不是"系统变卡"的直接原因。
- **它不可逆。** WebView2 把 70 个 DLL 加载进了宿主进程，而 Windows 和 .NET 都不支持卸载已加载模块。所以是"用一次就留下"，退不回去。

**结论：这条不违背你"常驻不能拖慢系统"的要求。** 真正的重负担只有"主窗开着的那段时间约 440 MB"，而那段时间你本来就在看它。

## 4. 推荐方案与四条实现规则

### 规则 1 —— 懒加载，**不做**开机预热

先说清一个二选一，这是本次实测最实际的收获：

- **预热确实有效。** 三轮实测（每轮都新建 Environment）CoreReady 从 **4116 ms → 2113 ms → 1007 ms**。因为每轮 env 都是新的，所以提速来源是"70 个 DLL 已加载进进程"这件事，不是 env 复用——也就是说，常驻期内静默预热一次，之后每次开主窗都能省掉这部分。
- **但它救不了页面渲染。** 预热后 CoreReady 只要 1.0 s，可首帧仍然要 **3.1 s**——中间那 2.1 s 是 v4 页面自己渲染 365 格热力 + 104 键 + SVG 图表的开销，消不掉。

所以预热只能把 4.6 s 变成 3.1 s。二选一变成：

| | 开机预热 | 纯懒加载（建议） |
|---|---|---|
| 常驻状态 | boot 后就多背 +70 MB | 常驻零成本 |
| 第一次打开主窗 | 快约 1.5 s | 慢约 1.5 s（且反正有骨架屏） |
| 之后每次打开 | 快约 1.5 s | 快约 1.5 s（第一次已付过 +70 MB） |

**建议纯懒加载**：+70 MB 早晚要付（第一次开窗就付了），但没必要在你可能一整天都不开主窗的情况下，开机就先垫上。这更贴你"轻量常驻"的初衷。

### 规则 2 —— 主窗必须上骨架屏

首帧 3.1 s 是硬数字，且已排除预热能救的可能。打开主窗时先用原生 WPF 画壳和已知的 KPI 数字（这些数据本来就在 C# 手里，无需等 WebView2），页面就绪后再替换。这一条不做，整个升级的体感会被那 3 秒毁掉。

### 规则 3 —— 速记捕获窗保持原生 WPF，绝不能迁 WebView2

首帧 3.1–4.6 s 是铁证。全局热键那条路径要求"按下去就出现"，WebView2 完全不可能满足。现状 `Views/QuickNoteWindow`（89 行 XAML）已原生实现，保持不动。这条同时与 `CONTEXT.md` 里"捕获窗"的定义一致，不需要改词汇。

### 规则 4 —— 走 Evergreen 运行时，不打包固定版

固定版会把包从 176 MB 吹到 356 MB。Evergreen 实测本机已有 153.0.4234.48，Win11 与装了 Edge 的 Win10 基本都有。启动时探测一次，缺失就显示原生降级页 + 安装引导，不做静默失败。

## 5. 第二个拦路虎：数据层

这一条与 UI 无关，但优先级更高。按键库 **192.7 万行**、`PressTime` 无索引，实测：

| 方案 | 年度热力图（139 天 × 104 键） | 单日下钻 | 整年合计 | 代价 |
|---|---|---|---|---|
| 现状（`substr()` 分组、无索引） | **4,216 ms** | — | — | — |
| 只给 `PressTime` 加索引 | 2,532 ms | — | — | 索引 **+163 MB**，基本无效 |
| 加实体列 `Date`/`Hour` + 覆盖索引 | 246 ms | — | — | 表体积翻倍 |
| **预聚合日表（11,121 行）** | **12.9 ms** | **0.3 ms** | **0.7 ms** | 一张小表 + 写入路径改造 |

**必须做预聚合表。** 加索引是死路——`substr(PressTime,1,10)` 是函数调用，索引用不上分组，白白多占 163 MB。

顺序反了的话，你会得到"界面很好看、点一下转圈 4 秒"的结果。注意 v4 现在跑的是 mock 数据，**它的流畅度不构成真实体验的证据**。

**改法是否安全（开源后不是我一个人用）：已在真实库副本上演练验证，5 项判据全部通过，原始数据一字未改。** 细节见 `数据层改造-安全方案.md`。

另外，真实数据只有 4.5 个月（2026-05-04 起，139–140 天），v4 画的是 12 个月 → 7 个月是空的。见第 7 节第 3 问。

## 7. 需要你拍板的 3 件事

1. **确认走路线 C（混合）？** 实测支持这个选择：包体积只 +1.0 MB、常驻成本可控、v4 资产 90% 复用。A 的唯一优势是零新增运行时依赖，代价是代码量翻倍 + 观感打折。
2. **开机预热做不做？** 我建议不做（规则 1 有对比表）。做了 = 常驻先垫 +70 MB 换第一次开窗快 1.5 s。
3. **年热力图的空态怎么处理？** 真实数据 4.5 个月、v4 画 12 个月 → 7 个空月。默认范围收窄到有数据的天数，还是保留整年接受空月？

## 附录：外部参照 —— BongoCat 是怎么做的

调查时间 2026-09-21，对象 [vladelaina/BongoCat](https://github.com/vladelaina/BongoCat)（开源桌面宠物，v1.11.0）。

**它一点 Web 技术都没用。** 技术栈是 C11 + SDL3 + OpenGL，设置窗用 **Nuklear**（即时模式 GUI 库）在独立的 OpenGL 窗口里自绘；Live2D Cubism SDK 可选（缺了就降级成诊断后端）。C++17 只用于 Live2D 桥接。

### 「现代 UI」是怎么做出来的

| 层 | 实现 | 体量 |
|---|---|---|
| 主题令牌 | `src/ui/theme/ui_catime_theme.c` 里一个 `BongoCatUIPalette` 结构体，20 个语义令牌（background / surface / field / border / border_subtle / text / muted / accent / accent_hover / accent_pressed / pink / hover / selection / danger / …），浅色深色各一套；`geometry()` 里调圆角（窗口 12、按钮 10、输入框 10、下拉 10、可选项 9、滚动条 3）和间距；最后 `nk_style_from_table()` 一次性套上。还适配了 Windows 高对比度模式（读系统色）。 | `src/ui/theme/` 共 **24 KB C** |
| 控件层 | Nuklear 自带控件不够用，所以**整套手写**：文本输入 5.7 KB、数字输入 5.2 KB、开关 5.1 KB、下拉 9.0 KB、**滚动条 5.5 KB**、可选项、标签页、图标、对话框、通知、模型卡片 13.2 KB + 自绘 4.3 KB、DPI 缩放 11.2 KB、拖拽实时重排 5.8 KB、字体 4.2 KB | `src/ui/preferences/` **71 个文件、346 KB C** |
| 字体 | 用系统字体，**自己烘焙字体图集**：按语言算字形范围（CJK/韩文各自 fallback），DPI 变化要重新烘焙（带 1 秒退避重试），且**不能在渲染帧中途重建**（`font_reload_pending` 标志） | — |

配色明显是 GitHub Primer 风格（深色底 `0x010409`、强调蓝 `0x54AEFF`、品牌粉 `0xF77DAA`）。主题名 `ui_catime` 来自作者另一个项目 Catime —— 这套设计资产是跨项目复用的。

### 换来的收益：体积

| 产物 | 体积 |
|---|---|
| Windows x64 安装包 | **5.9 MB** |
| Windows x64 便携版 | 6.2 MB |
| macOS arm64 | 6.0 MB |
| Linux AppImage | 10.6 MB |

### 对我们这份评估的三条启示

1. **它的 6 MB 不是"没用 Web"换来的，是"用 C、不带运行时"换来的。** 我们的自包含包 76 MB 里约 71 MB 是 .NET 运行时与框架，应用自身只有 5.1 MB。**体积问题跟 WebView2 无关**（它只加 1.0 MB），跟"要不要自带运行时"有关。
2. **它的"现代 UI"是 346 KB 手写 C 代码换来的。** 我们走 WebView2 等于把这笔钱省掉——输入框、开关、滚动、文字排版、DPI、国际化字形全由浏览器提供。这从另一个方向印证了路线 C。
3. **但如果目标真的变成 6 MB，那不是"升级 UI"，是另起一个项目。** 要放弃 WPF 和 .NET，用 C/C++ 重写事件循环、全局钩子、SQLite 访问和整套控件。评估里路线 A（原生 WPF 重写）的工作量（5,000–7,000 行）比这个还小一个量级。
